What is in place, and what is not

Everything on this page can be evidenced. The second half, about what we do not have, is here for the same reason as the first.

Last reviewed 2026-09-16

Your data is separated at the database, not by a filter

Every tenant has its own database schema, and every request is routed to it before a query runs. There is no query anywhere that returns another firm's rows if somebody forgets a WHERE clause, because the isolation is not a WHERE clause.

The audit trail cannot be rewritten

Authentication events and API access are recorded on a plane the application itself cannot edit or truncate. That is enforced by database triggers rather than by the application agreeing not to, which is the only version of it worth having: an audit log the application can rewrite proves nothing about the application.

Signing in

  • ✓Time-based one-time-password MFA, with a workspace-level control over whether it is required.
  • ✓Throttling that counts failed MFA challenges, not only failed passwords. Counting passwords alone leaves the second factor open to grinding, which is the interesting half to attack.
  • ✓Federated identity over OIDC, with a break-glass path that is itself audited.

What runs before a release reaches you

  • ✓Every commit is scanned for secrets, and the deploy refuses a revision that has not passed that scan. Not a warning, a refusal.
  • ✓Dependencies are audited weekly and automatically. The first run found 48 known vulnerabilities; they were remediated the same day.
  • ✓Every deploy re-proves the arithmetic. An invariant sweep runs across every live fund afterwards, and it records its own verdict whether anyone is watching or not.

No third-party code in the product

The application loads no analytics, no trackers, no advertising and no external fonts. The one exception is a cookieless counter of page requests, which stores nothing on your device and cannot see into a workspace: it records that a page was requested, never what the page showed. Everything that touches data is named on the sub-processors page and in the privacy notice.

What we do not have

The current limitations, and what changes each one.

  • ✓No SOC 2 report. Planned for when a customer's procurement requires one.
  • ✓No third-party penetration test. An internal security audit in August 2026 found one critical and twenty high-severity issues, all closed.
  • ✓Single availability zone. The database is not currently replicated across zones, so a zone failure is downtime rather than a failover. Backups and the pre-deploy snapshot are the recovery path.
  • ✓No published uptime figure. There is no measurement period long enough to quote one honestly.
